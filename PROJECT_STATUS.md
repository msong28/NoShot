## Milestone 14 — Account deletion & privacy — done (2026-07-22)

Built independently on branch `delete-accounts`, in parallel with the cofounder's ledger/redemption work on a separate branch (see the historical-record note above for two near-miss collisions between the two efforts, both caught before either reached the live database incorrectly). Summary:

- `supabase/migrations/20260722120000_account_deletion.sql` (renamed from its original `20260722090000_account_deletion.sql` during merge -- see the historical note above): `delete_account_request()` (SECURITY DEFINER, same house style as every other RPC) anonymizes the caller's `profiles` row in place rather than hard-deleting it -- per PRD §9.5, counterparties need to retain coherent pseudonymized history, and profiles.id is referenced by friendships/group_members/bets/ledger_entries/etc. with `on delete cascade`, so an actual row delete would have silently destroyed other people's transaction history too. Scrubs `username`/`display_name`/`birth_year`/`age_acknowledged_at`, sets `status = 'deleted'` and `deleted_at`, cancels the caller's own pending friend requests and declines pending group invites (same "clean up dangling pending state" reasoning `block_user()` already uses), and revokes sessions via `delete from auth.sessions where user_id = auth.uid()`. Accepted friendships and active group memberships are deliberately left untouched. Also tightens `profiles`' direct-UPDATE grant from a blanket row grant down to column-level (`display_name`, `birth_year`, `age_acknowledged_at` only) -- a pre-existing gap from Milestone 1 that would otherwise have let a client set `status = 'deleted'` directly, bypassing anonymization and session revocation entirely.
- No PRD requirement gates deletion on outstanding bets/obligations the way `GR-03` gates leaving a group -- confirmed deliberately not adding that gate, since anonymize-not-delete is exactly what makes deleting with open obligations safe.
- `supabase/tests/account_deletion.test.sql`: 12 pgTAP assertions -- anonymization fields, idempotency (can't delete twice), the pending-vs-accepted friendship split, the pending-vs-active group membership split, direct `status` update denied while `display_name` stays directly updatable, session revocation, anon has zero execute access. `scripts/test-db.sh`'s inline `auth` schema stub gained a minimal `auth.sessions` table so this is testable locally at all.
- `src/hooks/use-account-deletion.ts`, `src/app/delete-account.tsx` (a dedicated screen, not just a modal, given how irreversible this is -- explains what's anonymized vs. what counterparties keep, gated behind the existing `ConfirmationDialog` for the final step), reachable from a new destructive "Delete account" entry on the Account screen. Reuses the same `signOut()`-then-let-the-root-navigator-redirect pattern the Account screen's own sign-out button already relies on.
- `src/app/privacy-policy.tsx`, `src/app/terms.tsx`, `src/app/community-guidelines.tsx`: placeholder legal documents, each opening with a shared `LegalDisclaimer` component reading "NOT LEGAL ADVICE — FOR COUNSEL REVIEW". Drafted to accurately describe what NoShot actually does today (no cash stakes, the real anonymization-not-deletion retention behavior, the tiered moderation posture) rather than generic boilerplate, since a wrong description would be worse than no description. Registered as ungated routes (reachable regardless of auth state, same reasoning as the invite-preview screen) and linked from a new "Legal" section on Account.

Known, deliberate scope gaps:

- No gate on deleting an account with outstanding bets/obligations (see above -- not a PRD requirement, and the anonymization model makes it unnecessary).
- Session revocation stops future token renewal immediately but doesn't retroactively invalidate an already-issued, not-yet-expired access token, since Postgres RLS decodes the JWT without re-checking session validity per request. Documented as a residual-window caveat in the privacy policy rather than silently overclaiming "immediate." Closing that fully would mean adding a status check to every RLS policy/RPC app-wide, which was out of scope for this milestone (and would have meant touching the bet/ledger files that are explicitly the cofounder's territory).
- Legal placeholder screens aren't linked from the sign-up flow yet (only from Account) -- a reasonable next step before store submission, not done this pass to stay scoped to what was asked.

## Milestone 11 — Redemption & forgiveness — done (2026-07-20)

What shipped:

- `supabase/migrations/20260720090000_redemption_forgiveness.sql`: `redemption_requests` (+ `redemption_status` enum: `pending`/`confirmed`/`declined`/`cancelled`), `forgiveness_events`, and `obligation_allocations` — the PRD's own named table (§8) mapping a redemption or forgiveness event back to the specific original ledger entries ("obligations") it draws down, with a per-source amount. This is what makes BAL-05's "user selection of underlying obligations" and per-source outstanding tracking possible, and what Appendix B's "redemption amount cannot exceed selected outstanding allocation" is checked against.
- `get_outstanding_obligations(counterparty, currency, group)`: what's left to redeem/forgive per original ledger entry, after subtracting whatever's already reserved (a pending redemption) or settled (a confirmed redemption or a forgiveness) against it.
- `request_redemption(allocations)` — debtor-only; locks each selected source row `FOR UPDATE` so two concurrent redemption requests against the same obligation can't both reserve the same outstanding amount (the second waits for the first's transaction to commit, then sees the real remaining amount). `confirm_redemption()`/`decline_redemption()` — creditor-only. `cancel_redemption()` — debtor-only, releases the reservation. Same propose/approve/decline/cancel shape as Milestone 10's manual obligations.
- `forgive_obligation(allocations, note)` — creditor-only, single atomic step. Unlike redemption, BAL-07 doesn't require the debtor's agreement to be forgiven, so there's no separate request/confirm pair — the reservation and the ledger write happen together.
- Both settlement paths reuse Milestone 9's signed-netting trick: a redemption or forgiveness ledger entry is inserted with debtor/creditor **swapped** relative to the original obligation, so `get_my_balances()` needs zero entry-type-specific logic to net it down correctly — it already just sums by direction.
- Scope note: only `bet_settlement` and `manual_obligation` entries are treated as redeemable/forgivable sources. `correction` is left out entirely — nothing writes that entry_type yet (defined in Milestone 9, still unused), and §8.1's own phrasing suggests it behaves more like a further deduction than a fresh obligation, which isn't a question this milestone needed to answer.
- `src/lib/redemption.ts`, `src/hooks/use-redemption.ts` (`useOutstandingObligations`, `useMyRedemptions`, and mutations for each RPC). The `/balances` screen's drill-down gained a "Settle up" section (per-obligation Redeem/Forgive, with an amount field defaulting to the full outstanding amount) and pending-redemption confirm/decline/cancel UI. Home's "Needs your attention" now also surfaces redemptions awaiting the caller's confirmation.
- UI scope note, same shape as Milestone 6's direct-1:1-only creation form sitting on top of a fully general N-way schema: the backend's `p_allocations` parameter accepts a batch of obligations in one call, but the UI acts on one obligation at a time (each "Settle up" row has its own amount field and button) rather than a multi-select batch flow. The schema/RPCs don't need to change if that's wanted later.
